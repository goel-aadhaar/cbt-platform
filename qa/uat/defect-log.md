### BUG-101 — An answer-key edit did not re-score the exams already sat

|                 |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UAT**         | S13-P1-09, S11-P1-13                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Severity**    | **P0 (data integrity)**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Issue**       | Editing a used question's `answerKey` with `confirm=true` triggered **no recalculation**. Stored `Result` rows kept the old totals, while `getReviewForStudent` recomputed each question's correctness **live** from the _current_ key.                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Why P0**      | The two halves of a candidate's own result screen stopped agreeing: the per-question marks in review no longer summed to the total printed above them, and the published rank still reflected the superseded key. A candidate reading their result would see arithmetic that does not add up, and an appeal against it would be unanswerable.                                                                                                                                                                                                                                                                                               |
| **Root cause**  | `QuestionsService.update()` had a _warning_ path for used questions (409 unless `confirm=true`) but no _remediation_ path. The parallel case — marking a question BONUS or DROPPED — already called `evaluate({ preservePublished: true })`; a key edit simply never did.                                                                                                                                                                                                                                                                                                                                                                   |
| **Fix**         | `QuestionsService` now injects `ResultsService` and, when an edit actually changes how the question scores, re-evaluates every affected exam that has results. "Actually changes" is compared against the stored value, not merely "the field was present", so re-sending an unchanged key is a no-op and a typo fix in the statement never re-scores a concluded paper. `preservePublished` keeps an already-visible result visible — a correction should update what a candidate sees, not yank it back into review. The affected exams are returned to the caller as `recalculated`, so the recalculation is visible rather than silent. |
| **Retest**      | `qa/uat/answer-key-checks.py` — **27/27**. On a paper whose scores are hand-computable (keys A/A/A → 12 / 2 / −3): flipping q1's key to B rewrote the stored totals to 7 / −3 / 2, re-derived the ranks, kept all three results published, and made the **review screen's per-question marks sum to the stored total again** for every candidate. Restoring the key restored the original scores. The un-confirmed-edit safeguard still returns 409.                                                                                                                                                                                        |
| **Sensitivity** | The same suite was run against a build with this fix deliberately reverted: **18/27**, failing on exactly the symptom reported above (`sum=7 stored=12`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### BUG-102 — Re-evaluation re-cohorted a concluded exam

|                      |                                                                                                                                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **UAT**              | S13-P1-10                                                                                                                                                                                                                                                                                  |
| **Severity**         | **P0 (data integrity)**                                                                                                                                                                                                                                                                    |
| **Issue**            | `evaluate()` derived each result's `batchId` from the student's **current** batch. Moving a candidate between batches and re-evaluating rewrote a concluded exam's batch ranks against a cohort that candidate had never competed in.                                                      |
| **Why P0**           | Batch rank is a published, comparative figure. Re-scoring an exam for an unrelated reason — a bonus question, a key correction — would silently restate other candidates' standings in a paper that finished weeks earlier.                                                                |
| **Root cause**       | The evaluation read present-tense data for a historical fact. There was no snapshot of the cohort as it stood when the paper was sat.                                                                                                                                                      |
| **Fix**              | `evaluate()` now reads the `batchId` already recorded on any prior `Result` for the attempt and reuses it, falling back to the student's current batch only for an attempt being scored for the first time. The batch a result carries is therefore the batch the candidate **sat under**. |
| **Retest**           | Same suite. A candidate ranked 1st in their batch was moved into a batch where they would rank 3rd, and the exam re-evaluated: batch rank stayed 1, scores were unchanged, and no other candidate's rank moved.                                                                            |
| **Sensitivity**      | With the fix reverted the same assertion reports `batchRank=3`.                                                                                                                                                                                                                            |
| **Scope correction** | The original report also named `maxScore` re-derivation from current sections. On investigation there is **no reachable path**: section marks cannot be edited through the API once an exam leaves DRAFT. The defect was narrowed to batch grouping rather than left overstated.           |

### BUG-120 — One incidental violation ended the exam, on the default setting

|                     |                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UAT**             | S04 (CBT engine), S15 (proctoring)                                                                                                                                                                                                                                                                                                                                                                               |
| **Severity**        | **P0**                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Issue**           | `maxViolations` of 0 — the schema default for **every** exam — auto-submitted the candidate's paper on the _first_ proctoring violation.                                                                                                                                                                                                                                                                         |
| **Why P0**          | The schema field documents the exact opposite: "`maxViolations` > 0 auto-submits + flags the attempt once reached (**0 = warnings only, no auto-submit**)". So on the default configuration, a candidate who alt-tabbed once, or whose browser dropped out of full screen for any reason, had their exam terminated and submitted. An attempt cannot be restarted. The banner also read "Warning 1/0 Violation". |
| **Root cause**      | `useProctoring` tested `next >= maxViolations`. With `maxViolations` 0 that is `1 >= 0` — true on violation one. The limit was never guarded on being set at all.                                                                                                                                                                                                                                                |
| **How it surfaced** | Not by reading the code: the browser suite kept losing its own attempt mid-run, and the reason turned out to be the runner auto-submitting on the first synthetic focus change.                                                                                                                                                                                                                                  |
| **Fix**             | `maxViolations > 0 && next >= maxViolations`. With no limit configured the violation is recorded and warned about, and the message says what actually happens ("recorded for the invigilator") instead of threatening an auto-submit that will never come. The header badge now reads "1 Violation Recorded" rather than "1/0".                                                                                  |
| **Retest**          | `S04-P0-31` in the browser suite, in all three browsers: fire the events a browser fires when a candidate alt-tabs, then assert the paper is still open. Result: `still sitting=true, submitted=false, banner=1 VIOLATION RECORDED`.                                                                                                                                                                             |

### BUG-123 — A request could wait forever for a database connection

|                     |                                                                                                                                                                                                                                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UAT**             | S20-P0-13, S21 (performance)                                                                                                                                                                                                                                                                             |
| **Severity**        | **P1 (availability)**                                                                                                                                                                                                                                                                                    |
| **Issue**           | The pg pool was created with `max` only. node-postgres defaults `connectionTimeoutMillis` to 0 — wait forever — and nothing evicted a socket the managed database had already closed.                                                                                                                    |
| **How it surfaced** | A `POST /attempts` during testing hung for **255 seconds** and then returned a 500: `Connection terminated unexpectedly`. The pool had handed out a connection Neon had already dropped.                                                                                                                 |
| **Why it matters**  | "Wait forever" is the worst behaviour available during an exam: the candidate gets a spinner rather than an error they can act on, and requests pile up behind a database that is not answering.                                                                                                         |
| **Fix**             | `connectionTimeoutMillis: 10_000` so a request fails fast and visibly; `idleTimeoutMillis: 30_000` so an idle socket is dropped well before the provider drops it; `keepAlive: true` so a connection idling behind NAT is not silently killed. Each is commented with the observation that motivated it. |
| **Retest**          | Full API suite re-run on the rebuilt server: 33 P0-security + 17 roster + 9 search + 11 concurrency + 27 answer-key + 30 CBT-engine assertions, no connection errors.                                                                                                                                    |
